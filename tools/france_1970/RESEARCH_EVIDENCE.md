## Actionable implementation checks

No actionable target-ID, target-year, project-name, or DLC-branch mismatch found in the concept. `any_unresearched_target` prevents offering a research-only node when all listed targets in its active variant are already researched; `completed_required_projects` excludes the gated research until the actual native project completion trigger is true. If a listed target is still unresearched but its ordinary prerequisite chain is not yet complete, the bonus can sit unused until that target becomes researchable; this is native banking behavior and the concept makes no reassignment promise. If that is undesirable, add an explicit target-availability (`can_research`) eligibility condition and mirror it in the completion guard. Do not silently assume `has_tech` means reachable.

The concept JSON and builder remain a specification, not compiled game script. Before implementation, verify the emitter maps each variant to one separate guarded native `add_tech_bonus` block, translates `not_has_dlc` to a native `NOT` wrapper, and expands each required project to `is_special_project_completed = sp:<id>`. Apply the same active-variant, unresearched-target and completed-project tests in availability and completion reward. Keep `uses = 1` once for the repeated exact-ID list; no automatic fallback or project grant should be emitted.

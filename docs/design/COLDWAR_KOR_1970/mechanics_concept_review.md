# South Korea 1970–1990 Concept: Independent Mechanics Review

Read-only review of the current `COLDWAR_KOR_design.json`, `COLDWAR_KOR_native_recipes.md`, builder/contract sources, and active MD Cold War source. No loaded game scripts or parent-authored concept files were changed. This review addresses mechanical traceability and concept consistency, not balance approval or implementation.

## Latest re-audit: 206-node design plus native recipes

The updated design and `COLDWAR_KOR_native_recipes.md` close the earlier concept-level gaps about the security caretaker, legal civic participation, revolutionary ratification, action-ID coverage, KJP slot mapping, membership ownership, and the inter-Korean legacy adapter. The new helpers are explicitly labeled proposed content. These are now **specified providers awaiting implementation approval**, not unexplained/missing concept mechanics:

- The action catalog declares every action used by the 206 nodes. Two declared actions are currently not referenced directly by a focus action: `joint_ratification` is nested in the conditional Korean-settlement route, and `constitutional_party_guarantees` is invoked by KJP settlement. Confirm those indirect mappings in the eventual emitter.
- `gate_definitions` contains one exact country-scope proposed trigger for each focus. Student/civic slots 5 and 19 check explicit legality flags; slot 4 checks the revolutionary-settlement receipt; slot 7 checks the security-directorate ratification receipt; and KJP checks slot 0 plus Kim Jong-pil as actual incumbent. The recipe specifies the new `COLDWAR_KOR_1970_set_leader` branch for slot-0 KJP and explicitly preserves the modern slot-14 NACF path. This resolves the prior slot mismatch at design level; do not present the proposed dispatcher as current runtime code.
- The entry-route catalogue now specifies civic legalization, a ratified revolutionary transition and a KCIA caretaker transition via the existing `change_ruling_party_effect` inputs, with their costs and no automatic popularity/victory grant. This resolves the prior missing-route premise at concept level. Slot 7 remains an explicitly exceptional alternate caretaker use of the registry’s KCIA power-bloc slot; keep the proposed elections-disabled term and “no backing alone” requirement intact.
- The new `COLDWAR_KOR_confederal_member` idea is zero-stat status granted bilaterally only after signed sovereign framework or verified legacy acceptance. The secretariat proposed availability and completion guards both require the membership idea in KOR and NKO. Legacy NKO agreements are grandfathered only from genuine bilateral native acceptance and do not create a new charge, duplicate reward, or manufactured legacy flag. These are specified compatibility rules; their glue code remains new.
- The economic schema now has one expense record per single-policy focus, distinct bilateral contract charges, explicit zero-clear replacement, and the original start-presidency/alliance replacement routes. Same-slot policy forks remain mutually exclusive through the prerequisite/exclusion graph, with sequential policy levels replacing the prior value.

### Final concept-level status

1. **The Park-branch settlement guard is now resolved at concept level.** Current JSON and recipe gate bodies for both `COLDWAR_KOR_can_emergency_decrees` and `COLDWAR_KOR_can_dynastic_presidency` test `has_country_flag = COLDWAR_KOR_constitution_yushin`; each JSON completion guard repeats that condition along with the once-only receipt. The controlled Fifth Republic press-consolidation gate and completion guard likewise require `COLDWAR_KOR_constitution_controlled_fifth`. Their prose conditions now agree with the proposed exact checks. These remain proposed guards to implement, not loaded game code.

2. **Conditional-settlement routing is specified, with an implementation constraint.** The `conditional_peninsula_review` action definition now clearly says a signed secretariat/trade agreement reveals joint ratification, while definitive refusal/expiry gives only a domestic review and +25 PP. Preserve `joint_ratification` as that signed-outcome sub-action, not a generic standalone decision. The current OR prerequisite and refused/expired bypasses support reachability; runtime must check the exact pair/signature/response and must not grant the joint reward on the fallback path.

3. **Building slots are still a runtime/scenario check, not a design contradiction.** State IDs and building types remain plausible, and recipes specify ownership/control/free-slot guards. Current history records do not establish the actual 1970 levels or capacity, so a later implementation must evaluate the guard after the 1970 setup and make charge/construction atomic.

4. **Multilateral contracts require one actual recipient ledger entry per tag.** The contract catalogue declares the multi-party intent, and the NKO adapter avoids duplicate legacy rewards. The proposed event implementation still needs a separate signature/payment/effect record per partner for `nordpolitik_recognition`, `neutrality_guarantees`, and `vietnam_withdrawal_settlement`; never use their descriptive recipient string as one scope. This is a typed implementation requirement, not an unprovided contract term.

5. **Static approval-stage providers are not loaded runtime APIs.** The recipes are sufficiently named to implement, but remain new providers: leader dispatcher/migration, policy refresh and dynamic modifiers, weekly expenses/income integration, political sync, offer lifecycle/expiry, legal-entry decisions, transition events, focus bypass blocks, membership ideas, KOR/NKO shared ledger and atomic construction handlers. No claim is made here that any of those providers exists in loaded game files.

The exact modifiers and source readers are audited below. The civilian productivity correction is verified against current MD code and the revised player-facing label. No current concept-level issue was found in the revised fork/join policy exclusivity, expense-slot uniqueness, party/country reader scopes, bilateral legacy-grant rule, or the checked Yushin/Fifth Republic settlement guards. Named new providers and integration hooks are specified conceptually, not present in runtime.

### 1. Party ownership proposal is a migration, not existing runtime behavior

The design and recipe correctly keep party migration proposed. The present registry establishes DRP 0, NDP 1, Forties Standard-Bearers 2, USP 3, RPR 4, June Third Generation 5, KCIA 7, EPB 13 and Army 22. However, current `KOR_political_leaders.txt` routes YS through slot 1, DJ through slot 3, Chun through slot 22, and the native pool/retirement machinery also tests YS at 1 and DJ at 3 (`mdcw_historical_native_pools.txt` and `mdcw_historical_retirement_alternatives.txt:92–93`). Roh was not found in the current KOR pools. The recipe now proposes the slot-2 YS/DJ route, Kim Chul/USP slot 3, dated Roh addition, KJP slot-0 dispatcher and a preserved modern slot-14 route. Implementing that proposal still requires coordinated registry/population, coalition, leader-pool/routing, retirement-alternative and incumbent-trigger changes; the JSON and recipe do not change those live files.

More immediately, the “KCIA · an exceptional security cabinet” group gates on `ruling_party = 7`. Registry slot 7 denotes the KCIA power bloc rather than an ordinary governing party. The new recipe now specifies an explicit, elections-disabled caretaker transition to slot 7, with receipt flag and cost. This is a deliberate alternate-history state, not an ordinary legal-party route; its new KOR caretaker dispatcher and political-array behavior remain proposed implementation. Treating slot 7 as generally electable would still contradict the registry.

The Army/DJP path on slot 22 is grounded in an existing slot and Chun pool; the new recipe supplies the missing proposal for dated DJP/Roh identity and office routing. Any YS, DJ, Chun or Roh focus guard must continue to check the installed incumbent (the existing `has_country_leader = { name = ... ruling_only = yes }` pattern), not merely a party-popularity value or candidate pool.

### 2. Starting-spirit transition coverage in the first-pass review (superseded by the 206-node update)

The first 194-node draft had no replacement route for `start_presidency` or `start_alliance`. The updated JSON now declares presidency replacements and an alliance replacement after strategic autonomy or accepted U.S. assurance, as described above.

The remaining requirement is implementation: ensure the start callback grants each start spirit once, and the acceptance callback—not offer dispatch—resolves the alliance exposure. `start_presidency` must not be granted as though Yushin were already active in 1970.

### 3. Weekly cost schema in the first-pass review (superseded by the 206-node update)

In the first 194-node draft, weekly expense was focus-wide and had no policy-slot identity; the initial contract enrichment copied it to each policy entry. The updated 206-node JSON removes that enrichment field and gives each one-policy focus a single `effects.expense_commitment` record, with explicit owner, qualified slot, replacement and zero-clear semantics. No current focus has multiple policies or a positive weekly amount without a policy record.

The native economy is reusable: `calculate_additional_expense_rate` resets and reconstructs `additional_expenses_rate` (`00_money_system.txt:3663–3681`) and the resulting weekly expense enters native treasury accounting. The `COLDWAR_KOR_weekly_cost` refresh/aggregation logic and owner qualification are still new KOR adapter work, not existing MD/KOR APIs. The updated data model is now clear enough to implement one record per owner+slot; keep the contract commitments separate from domestic policy slots and do not double-count partner payments.

Money values use billions of dollars in the native economy. Thus `0.001`, `0.002`, `0.003`, and `0.004` mean $1m, $2m, $3m and $4m per week. Current concept monetary literals reviewed are within the project’s five-decimal limit; keep native weekly units in both runtime and player-facing summaries. The named cost values and expiries in the proposed bilateral contracts must also reconcile with payer and recipient effects (see the contract note below).

### 4. Fixed-state construction is not yet proven capacity-safe in the 1970 setup

The concept explicitly requires ownership, control and room for each intended building, and avoids a silent alternate-state grant. That is the right guard. The selected building types are standard HOI4/MD types: infrastructure, industrial complex, arms factory, radar station, anti-air building and dockyard. The chosen states are valid Korean state IDs: 604 Gyeonggi, 605 Yeongnam, 606 Chungcheong, 607 Honam and 608 Jeju. The target state-history files contain examples of the relevant building records (e.g. 605 has a dockyard; 604 a radar station; 608 a radar station), but those recorded levels are not evidence of the effective 1 January 1970 levels after the scenario setup. These state files also do not establish remaining building slots for each planned reward.

Before an implementation emits `add_building_construction`, resolve current owner/controller, existing level, state building-slot capacity, type limits and access/coast requirements after KOR’s 1970 scenario initialization. In particular check planned additions in 605 and 608 against their historical dockyard/radar records and any scenario-specific overrides. The concept’s atomic payment+construction language is a proposed adapter contract; no such KOR helper exists yet. A focus should only be offered/completable when the state can actually accept the building and the same accepted outcome pays the displayed treasury price once.

## Modifier and unit audit

The builder reads tokens from all target idea/dynamic-modifier/modifier-definition files and asserts that each appears as a top-level modifier key (`COLDWAR_KOR_build_concept.py:625–631`). That is a useful vocabulary check, but it does not prove the key has a reader, a country scope, the intended unit, or the proposed result. I found no unsupported key among the current 34 distinct keys used by the 206 focus nodes and starting spirits; `COLDWAR_KOR_modifier_evidence.json` now includes the civilian productivity field as well. The recipes classify MD custom modifiers by their actual reader and standard HOI4 national modifiers by native handling. The intended values still need truthful labels and source-aware aggregation in the runtime adapter.

## Replacement and finite-lifecycle mechanics

The concept’s owner-slot model (earned slots retained; only current owner contributes; refresh on government change/load/monthly failsafe; no one-time grant in refresh) is sound as an implementation constraint, but it is not a current KOR system. The concept must implement the active owner resolution, trigger it on all relevant political transitions and load, and ensure returning parties can re-activate their retained slots without duplicate modifiers. Completed construction, event receipts and one-time treasury/PP effects must remain behind once-only flags.

For focus policy slots, the JSON already uses named slots and the current contract-enrichment code writes a `qualified_slot` of `group:slot`. This supports replaceability as data, provided the runtime stores one value per owner+slot and replaces rather than adds values. However, bilateral contract benefits also need their own distinct signed-agreement owner/key and expiry/termination path; they must not be erased by a domestic government slot update, nor survive an expired or invalidated treaty indefinitely.

The updated model now declares the presidency, alliance and other start-slot transitions. Their grant/removal and owner-refresh code remains proposed and unimplemented.

## Offers and bilateral contracts

The contract module is explicitly marked as approval-stage design, not installed events. That distinction is correct. The contract records distinguish dispatch from acceptance, specify 60-day expiry, no-charge refusal, revalidation, once-only signing, and bilateral invalidation on war or signatory departure. These conditions still require actual event/decision code, recipient-side scope correctness, treasury presentation and cleanup. The existing NKO channel/confederation pathway is NKO-owned and cannot be treated as a generic KOR offer API. Inter-Korean actions need to converge on the existing recipient-consent framework or a fully scoped compatible bilateral handler; neither country should receive benefits merely because KOR completed a proposal focus.

The current `family_reunions` data clarifies the two-sided payment: KOR pays through the top-level KOR amount; NKO pays through the recipient effect; the description says each side’s amount. `limited_trade` similarly records KOR payment and recipient income. Keep these distinctions explicit in the acceptance option effects. Contract metadata is not executable proof.

For any “accepted contract” policy, use the contract’s actual signature flag and recipient pair, not a generic focus completion receipt. The anti-duplication rules currently say proposals shared by DRP/RPR/Roh/common routes use one ledger and counterpart NKO initiation resolves the same signature; those are new transaction-system requirements, not existing effects. The agreement benefits must end when the contract expires or is ended, while permanent one-time payment/building benefits must never replay on renewal.

## Current builder boundary and confidence

`COLDWAR_KOR_build_concept.py` converts shorthand metadata into a design JSON/manifest and checks that icon/modifier names exist in source. The native-plan stage now records proposed exact native focus guards/leaves, action routing and named helper contracts in approval-stage JSON/Markdown; these are design specifications, not executable HOI4 game files. The builder does not install native focus completion effects, dynamic modifiers, starting-idea grants/removals, party migration, offer events, action decisions, weekly expense aggregation or state-capacity guards. `COLDWAR_KOR_contracts.py` enriches the approval-stage JSON but states it is not installed. Thus the revised concept now specifies the new providers, but all `COLDWAR_KOR_*` ideas/modifiers/flags/variables, effect/trigger helpers, owner refresh, agreement handlers, contract lifecycle, election/succession integration and construction/payment atomicity still await implementation approval; none is an existing KOR API.

Source evidence verifies the current 1970 KOR start remains DRP slot 0 and Park incumbent, with the target generic 1970 tree in history. The current concept graph has 206 nodes and 34 distinct modifier keys. Static source inspection cannot prove HOI4 parser acceptance, actual state-slot availability in the scenario, correct game-scope execution, displayed rounded values, diplomacy event behavior, or existing-save migration. Those require a later implementation audit and game test; no runtime test was performed here.
